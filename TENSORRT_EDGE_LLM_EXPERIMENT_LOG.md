## OpenAI endpoint decision

The current NVIDIA checkout contains an experimental FastAPI server with:

- `GET /health` and `/health/ready`
- `GET /v1/models`
- `POST /v1/chat/completions`, including SSE streaming
- bearer authentication through `--api-key`
- OpenAI-shaped tools/tool calls and Qwen reasoning parsing
- one active generation request at a time with a bounded queue

The stock `tensorrt-edgellm-serve` command is checkpoint-native. It explicitly rejects ONNX directories and existing engine directories, then runs the checkpoint-direct builder and caches its own runtime bundle. Therefore it cannot directly serve the ONNX-built engine from this experiment.

The repository's native Python binding does support constructing `LLMRuntime` from an existing engine directory, optional multimodal engine directory, and checkpoint/tokenizer directory. Recommended path: build the runtime with Python bindings on the Jetson, generate the TensorRT engine from the transferred ONNX, and add a narrowly scoped engine-backed initialization path to NVIDIA's existing server while retaining its protocol, authentication, streaming, queue, tool, and error-handling code. Do not create a per-request `llm_inference` subprocess wrapper because that would reload the engine and destroy practical latency.

Alternative path: use stock `tensorrt-edgellm-serve` with the original or compatible quantized checkpoint and allow it to rebuild a checkpoint-native bundle. This is simpler but does not consume the ONNX export being transferred and would require the checkpoint weights on the Jetson.
